# 운행 중 휴대폰 위치·속도 동기화 (Trip Telemetry) — 설계안

> 상태: 승인됨 (저장소 = Blob만, 전송 간격 = 10분) · 작성 2026-10-25

## 1. 문제

| 구분 | 현재 | 결과 |
|---|---|---|
| 배차 상태 (신청·승인·운행중·반납) | 버튼 → 서버 액션 → 15초 폴링 | 정상 동작 |
| 운행 중 위치·속도·거리 | 전송 안 함 (2.5G 충격 시 1건만) | 지도·속도·GPS 주행거리 **멈춤** |
| 운행 시작 시 G값·RSSI | 고정값(1.01G, -48dBm) 기록 | 측정값처럼 보이는 가짜 값 |

## 2. 목표

1. 운행중(IN_USE)인 직원 휴대폰이 주기적으로 위치·속도를 서버에 보낸다.
2. 관리자 대시보드 지도·속도·"마지막 수신 n초 전"이 실제 값으로 갱신된다.
3. 반납 시 운행 요약(GPS 주행거리, 최고속도, 운행시간)이 예약 건에 남는다.
4. 위치 수신은 기존 직원 액션과 같은 신뢰 수준: 운행중 예약 + 해당 직원 일치 + 정확도·순간이동(>250km/h) 검사. 직원 로그인이 없으므로 위조 방지의 근본 해결은 M365 SSO 도입(범위 밖).

## 3. 흐름

```
[직원 폰] 운행 시작 ─▶ POST /actions dispatch.start  ─▶ 이 기기를 위치 전송 기기로 지정
          │
          ├─ watchPosition + Wake Lock(화면 꺼짐 방지)
          └─ N초마다 POST /api/fleet/actions trip.position {reservationId, employeeId, lat, lng, speedKmh, headingDeg, accuracyM}
                                    │
                         서버: IN_USE·직원 일치 검증 → 정확도 필터(>50m 버림) → 거리 누적
                                    │
[관리자 PC] 15초 폴링 /api/fleet/state ◀── 차량 lat/lng/speed/lastFixAt 병합
          │
[직원 폰] 반납 완료 ─▶ 운행 요약 저장(GPS km, 최고속도, 포인트 수)
```

## 4. 구성 요소

| 영역 | 변경 |
|---|---|
| 서버 도메인 | `domain/position.ts` 순수 함수: 검증·정확도 필터·하버사인 거리 누적·최고속도·무단운행 판정 재사용 |
| API | 기존 `/api/fleet/actions`에 `trip.position` 액션 추가 (zod 검증, 60초 내 중복 전송은 쓰기 생략) |
| 운행 시작/반납 | start: LIVE에선 G값·RSSI 고정값 기록 안 함 · return: GPS 요약 기록 |
| 저장소 | 기존 Blob DB 문서 (5장) |
| 휴대폰 화면 | 운행중이면 자동으로 GPS 시작, Wake Lock, "위치 전송 중 · 마지막 전송 n초 전" 표시, 권한 거부·GPS 끊김 경고 |
| 대시보드 | 차량별 마지막 수신 시각, 2분 이상 끊기면 "신호 끊김" 배지, 운행 요약 표시 |
| 테스트 | 도메인 단위 테스트(거리 누적, 토큰, 정확도 필터, 끊김 판정) + API 라우트 테스트 |

## 5. 위치 저장소 — 결정: Blob만 사용

10분 간격이면 30대 전부 운행해도 분당 약 3회 쓰기라, 별도 파일 없이 기존 DB 문서에 compare-and-swap으로 기록하고 대시보드는 기존 15초 폴링으로 읽는다(추가 읽기 0회). 아래는 검토했던 안.

위치는 30대 × 수십 초마다 쓰기가 발생한다. 현재 단일 JSON(Blob)에 매번 쓰면
(1) Blob 쓰기(put) 월 한도를 빠르게 소진하고 (2) 30대가 같은 문서를 두고 충돌(CAS 재시도)한다.

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A. Upstash Redis 추가 (권장)** | 위치·운행 요약은 Redis(Vercel Marketplace), 배차·마스터는 기존 Blob 유지 | 고빈도 쓰기에 적합, 충돌 없음, 무료 등급 존재 | 저장소 1개 추가(연결은 대시보드에서 클릭) |
| B. Blob만 사용 | 차량별 별도 파일 `positions/veh-N.json`, 60초 간격 | 추가 서비스 없음 | Blob 쓰기 한도 확인 필수, 대시보드 읽기 30회/폴링 |
| C. Supabase Postgres | 위치 이력 전체 저장, 이후 운행일지·리포트 확장 | 이력·조회 강력 | 변경 범위 가장 큼 |

## 6. 전송 간격 — 결정: 10분 (운행 시작 직후 1회 + 이후 10분마다, 반납 직전 1회)

GPS 주행거리는 10분 간격 직선거리 합이라 실제보다 짧게 나온다 → 반납 시 계기판 실사값이 기준, GPS km는 참고값. "신호 끊김"은 25분 이상 미수신.

| 간격 | 대시보드 체감 | 배터리·쓰기량 |
|---|---|---|
| 15초 | 폴링과 같은 속도 | 높음 |
| **30초 (권장)** | 지도 30초 단위 이동 | 중간 |
| 60초 | 거리 오차 증가 | 낮음 |

## 7. 웹앱 한계 (구현과 무관하게 남는 제약)

- 화면이 꺼지거나 다른 앱으로 전환하면 브라우저가 GPS를 멈춘다 → Wake Lock + "앱 화면 켜 두기"를 운행 절차에 필수로 추가. 끊기면 대시보드에 "신호 끊김"으로 표시해 숨기지 않는다.
- 백그라운드 추적이 꼭 필요하면 네이티브 앱(별도 프로젝트)이 필요하다.
- iPhone Safari는 Web Bluetooth 불가(차량 BT 확인은 이번 범위 밖).

## 8. 단계

| 단계 | 내용 |
|---|---|
| T1 | 도메인 + 테스트(RED→GREEN) |
| T2 | 저장소 어댑터(선택안) + `/api/fleet/position` + 라우트 테스트 |
| T3 | 운행 시작/반납 변경(고정값 제거, 요약) |
| T4 | 휴대폰 화면 자동 전송·Wake Lock·상태 표시 |
| T5 | 대시보드 마지막 수신·끊김 배지·요약 |
| T6 | 로컬 2탭 검증(가짜 위치 주입) → 커밋 → 배포는 별도 요청 시 |
